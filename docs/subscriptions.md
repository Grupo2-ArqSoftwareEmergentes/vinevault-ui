# Subscriptions: server-owned billing and entitlements

## Selected-space capabilities

`WorkspaceAccessService` is the shared capability/quota facade. `hasFeature()` requires an explicit server `true` from `overview.space.plan.features` (or the catalog entry for the context's effective purpose/tier) AND the required role permission. Unknown features fail closed; PRO alone never enables them. It exposes effective whole-space quotas without replacing `null` limits or deriving limits from visible rows. The root connects `SubscriptionApiService.connectWorkspace()` to the selected space so catalog and overview are available outside `/subscription`. Scope changes invalidate old overview capabilities synchronously, cancel obsolete reads and suppress stale overview publication; no localStorage flag, cancellation date or client clock grants or expires a plan.

Autocomplete always posts with the active `space_id` query parameter and refuses to POST without one. Autocomplete, assistant Chat/Sommelier, stock analysis, PDF/Excel exports and import/template handlers check shared capabilities as well as their role checks. `PlanFeatureNoticeComponent` offers an owner a selected-space Pro link, differentiates missing metadata from denied roles and can surface backend feature denials even if a prior capability snapshot was stale. File errors are decoded as structured JSON Blobs. `PLAN_FEATURE_UNAVAILABLE`, quota denials and structured role `FORBIDDEN` preserve the session; 413 suggests exporting by cava. Existing cavas/items are never filtered or deleted on downgrade: edits and stock reductions remain available, while quota projection blocks only growth beyond the server limit.

`/profile` links to `/subscription`, which shows membership spaces, account add-ons, active subscriptions and request history. Prices come only from `GET /api/v1/subscriptions/catalog` (`plans[].prices`, `addons[].prices`); cycle length is `cycle_days`, not an assumed calendar month. The soles-only UI preserves decimal strings and never calculates account billing totals or converts currencies. The simulated checkout alone previews catalog unit price × quantity using exact integer cents (BigInt); this preview is not an entitlement or a replacement for server billing amounts.

`GET /api/v1/subscriptions/overview?space_id=...&cellar_id=...` is the real subscription state. Cellar ID is optional context and is never sent without a space; PRO applies to the space and its cavas inherit it. Missing billing stays unavailable, not zero. The UI displays `billing.monthly_recurring_total` as Gasto mensual actual, `next_cycle_monthly_total` as Próximo ciclo and each `active_subscriptions[].monthly_amount/access_until` directly. Quotas (`limit: null` is unlimited) and management permissions come from overview and `/user/context`, never history or marketing limits.

Both dialogs use the shared two-column simulated checkout: a product summary on the left and Reactive Forms card details on the right, stacked/scrollable on mobile. It is explicitly a test environment with no real collection or automatic renewal. Test chips fill approved (`4242…4242`) or declined (`4000…0002`) synthetic cards. Required nonblank holder, 16 digits, a valid unexpired MM/YY and 3–4 digit CVV are checked before any request. The declined card never calls the API. Card data stays only in the dialog's form, is cleared on success/cancel/destruction and is never emitted, persisted, logged or sent to the backend. No production payment method is registered and the legacy mock checkout is not used.

Approved forms POST only the subscription fields, `currency: PEN` and `confirm_simulated_payment: true`. Idempotency keys are retained across network/server retries and replaced only for changed request parameters or IDEMPOTENCY_CONFLICT. Buttons, test-card chips, quantity changes and dismissal are locked while sending. Missing PEN prices or `simulated_payment_available: false` block checkout. The Pagar button displays the catalog-based checkout preview; the backend remains authoritative for the resulting quote and subscription.

A FULFILLED response with `entitlements_applied: true` closes checkout and triggers overview refresh followed by `/user/context` refresh through `SubscriptionApiService`, including entry points outside the plans page. UI state changes only from those responses. A 202 PENDING_PAYMENT response remains pending and never grants a plan, cupos or quotas. Refresh failures are reported without resending the mutation.

`POST /api/v1/subscriptions/{subscription_id}/cancel` schedules cycle-end cancellation. PRO cancellation requires the selected space's `can_manage_subscription`; account EXTRA_SPACE rows in authenticated overview billing are the purchaser's own subscriptions (the backend also enforces purchaser ownership). Duplicate/pending cancellation is blocked. The UI uses refreshed `cancel_at_period_end`, shows Se cancela al finalizar el ciclo and retains access, current spend and cupos through `access_until`. Next-cycle spend is supplied by the server. Expiry is not applied by a client timer; subsequent overview/context responses supply FREE and effective quotas.

The active paid subscription list is not part of the main page flow. Facturación → Ver suscripciones activas in the add-on card opens `ActiveSubscriptionsDialogComponent`, with a reactive count and compact PRO/add-on rows, singular/plural cupo labels, server amounts, access dates and renewal state. Only ACTIVE rows are counted; cancellation is offered only for auto-renewing, permitted rows. The modal reuses the page-owned cancellation handler and signals, so closing/reopening does not abort or duplicate a pending cancellation. It has an empty state, loading/error feedback, X/footer close controls, Escape/backdrop dismissal and focus restoration. It closes on space change or page destruction and cannot stack with checkout.

`GET /api/v1/subscriptions/requests?limit=20&offset=0` shows own pending, fulfilled and cancelled intents. The list is display-only, never a permission source. Both array and paginated responses are supported; array pagination permits a next page after a full result batch without inventing a total count. Subscription business errors (403/404/409/422) stay local and do not clear session/context; 401 follows the existing session reauthentication flow. `detail.code` selects actionable messages. No cancelled mutation is automatically retried.

Authenticated-shell scrolling and bottom clearance for the floating Assistant are preserved.
